# Задача 65 — Ядро системы плагинов

**Этап:** I — Плагины, сборка, релиз | **Зависит от:** 19, 04 | **Разделы ТЗ:** 9.1

## Цель
Обнаружение, валидация, загрузка и жизненный цикл плагинов из папки профиля так, чтобы падение плагина не роняло приложение.

## Что сделать
1. `plugins/manifest.py`: pydantic-модель `manifest.json` — `name` (идентификатор, проверка формата и уникальности), `version` (semver), `entry_point` (`module:ClassName`), `permissions` (список из фиксированного набора), `api_version` (int), описание, автор, зависимости от других плагинов и от Python-пакетов. Понятные ошибки валидации с указанием поля, а не трейсбек pydantic.
2. `plugins/discovery.py`: сканирование `profile/plugins/*/manifest.json` через `core/paths.py`, чтение манифестов, проверка совместимости `api_version` с текущим API (поддерживаемый диапазон, а не одно значение), сбор списка найденных плагинов со статусом (ок / несовместим / битый манифест / отключён) без загрузки кода.
3. `plugins/loader.py`: загрузка Python-пакета плагина — добавление папки в `sys.path` изолированно, `importlib` по `entry_point`, инстанцирование класса, проверка, что он реализует ожидаемый базовый интерфейс. Корректная выгрузка модулей плагина при unload, чтобы reload не тянул старый код.
4. `plugins/manager.py` — `PluginManager`: жизненный цикл `load → enable → disable → unload` с явным состоянием каждого плагина; каждый вызов в плагин обёрнут перехватом исключений — ошибка пишется в лог плагина, плагин помечается сбойным и отключается, приложение продолжает работать. События `PluginEnabled` / `PluginDisabled` / `PluginFailed` в шину.
5. Порядок загрузки и зависимости: топологическая сортировка по зависимостям из манифестов, детект циклов и отсутствующих зависимостей с внятным сообщением, отключение зависимого плагина при отключении того, от которого он зависит.
6. Включение и выключение без рестарта: enable/disable в рантайме с корректным снятием всего, что плагин зарегистрировал (команды, хоткеи, подписки на события), — за это отвечает менеджер, а не добросовестность плагина. Состояние «включён/выключен» хранится в БД или конфиге и восстанавливается при старте.
7. `plugins/installer.py`: установка из папки — валидация манифеста и структуры, проверка совместимости, список запрашиваемых разрешений для диалога согласия (UI в задаче 67), копирование в папку профиля, отказ при конфликте имён с существующим плагином. Плюс удаление с чисткой данных плагина.
8. Тесты на плагинах-фикстурах: корректный, с битым манифестом, с несовместимым `api_version`, падающий в `on_enable`, пара с зависимостью и пара с циклом.

`src/ayris/plugins/__init__.py`, `manifest.py`, `discovery.py`, `loader.py`, `manager.py`, `installer.py`, `base.py`, `tests/unit/test_plugin_core.py`, `tests/fixtures/plugins/*`

## Осторожно
- Плагин — сторонний код: любое обращение к нему в try/except, ни один хук не выполняется в UI-потоке без ограничения по времени.
- Загрузка плагина не должна засорять глобальный `sys.path` и `sys.modules` так, чтобы это ломало основной пакет или другие плагины.
- Установка из произвольной папки — вектор атаки: разрешения показываются пользователю до первого исполнения кода плагина, а не после.
- Не изобретать вторую систему регистрации действий: плагины идут через реестр из задачи 19.
- Почти всё здесь — чистая логика на фикстурных плагинах, и проверяется в песочнице. Исключение — снятие настоящих хоткеев и пути профиля Windows: такие тесты закрываются `pytest.mark.skipif(sys.platform != "win32")`, чтобы прогон на Linux оставался зелёным, а на windows-раннере отработал целиком.
- Фикстурные плагины пишутся в `tmp_path`, а не в реальную папку профиля: тест, оставивший плагин в профиле пользователя, отравляет следующие прогоны и живое приложение.

## Готово когда
- [ ] Плагины из папки профиля находятся, валидируются и грузятся, статус каждого виден в API менеджера.
- [ ] Плагин с битым манифестом или чужим `api_version` не грузится и объясняет причину.
- [ ] Исключение внутри плагина отключает только его, приложение работает дальше.
- [ ] Enable/disable в рантайме снимает и возвращает зарегистрированные команды и хоткеи без рестарта — **проверяет CI на windows-раннере**: регистрация хоткея идёт через WinAPI и в песочнице пропускается.
- [ ] Зависимости соблюдаются, цикл обнаруживается с понятным сообщением.
- [ ] Установка из папки проходит валидацию и возвращает список разрешений для подтверждения; тесты на фикстурах зелёные, ruff, black и mypy strict проходят.
