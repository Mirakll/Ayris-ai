# Задача 66 — SDK и песочница плагинов

**Этап:** I — Плагины, сборка, релиз | **Зависит от:** 65 | **Разделы ТЗ:** 9.2, 11

## Цель
Стабильный публичный SDK для авторов плагинов и песочница с системой разрешений и лимитами, чтобы сторонний код не имел больше прав, чем ему выдали.

## Что сделать
1. `plugins/sdk.py`: публичный API ровно по разделу 9.2 — `register_command(trigger, action)`, `say(text)`, `play_sound(path)`, `notify(title, body)`, `get_setting(key)`, `set_setting(key, value)`, `execute_action(action_name, params)`, `on_event(event_name, callback)` с хуками `on_startup`, `on_shutdown`, `on_command`, `on_wake_word`, `on_audio_level`, `on_timer`, `register_hotkey(combo, callback)`, `variables.get/set(scope, name, value)`. Каждому плагину выдаётся свой экземпляр контекста, знающий, кто его вызывает.
2. Стабильность API: `api_version` с правилами совместимости, публичные типы (`CommandSpec`, `ActionResult`, события) в одном месте, ничего из внутренностей приложения наружу не протекает. Изменения API — только через новую версию, старая поддерживается.
3. `plugins/permissions.py`: набор `network`, `fs`, `admin`, `audio`, `input`, `settings` (плюс отдельно `settings_read` / запись, `commands_register`) — проверка на каждом вызове SDK, отказ выбрасывает типизированную ошибку и пишет в аудит; согласие пользователя запрашивается при установке (диалог в задаче 67) и хранится вместе со статусом плагина. `execute_action` дополнительно сверяется с правами конкретного действия из реестра, включая `require_admin` и подтверждения из задачи 40.
4. `plugins/sandbox.py`: опциональный запуск плагина в отдельном процессе поверх инфраструктуры воркеров из задачи 05 — прокси SDK-вызовов через IPC, те же проверки разрешений на стороне главного процесса, краш процесса плагина не задевает приложение и перезапускается по политике. Режим выбирается в манифесте или настройках: in-process для доверенных, sandboxed для остальных.
5. Лимиты: таймаут на вызов в плагин (после которого вызов отменяется, а плагин помечается неотзывчивым), лимит памяти для sandboxed-процесса, ограничение частоты вызовов SDK от одного плагина, отдельный лог-файл на плагин.
6. `plugins/template/`: шаблон плагина для быстрого старта — `manifest.json`, `plugin.py` с одной командой и одним хуком, `README.md`, минимальный тест. Плюс генератор шаблона в новую папку, чтобы автор начинал не с чистого листа.
7. Документация SDK с примерами на каждый метод (для раздела в задаче 73), генерируемая из docstring'ов, чтобы не расходилась с кодом.
8. Тесты: каждый метод SDK на фикстурном плагине, отказ по каждому разрешению, таймаут зависшего хука, sandboxed-плагин с падением и перезапуском, попытка вызвать админ-действие без права `admin`.

## Осторожно
- Песочница на процессах — не полная изоляция: плагин остаётся Python-кодом. Не обещать в UI больше, чем реально ограничивается, честно писать это в документации.
- Разрешения проверяются на стороне главного процесса, а не в SDK-прокси внутри плагина, иначе проверку легко обойти.
- `say`, `notify` и хоткеи из плагина не должны блокировать UI-поток и перебивать активный диалог пользователя.
- Публичный API — контракт: любое переименование ломает чужие плагины, поэтому имена из раздела 9.2 сохраняются буквально.

## Готово когда
- [ ] Плагин-пример регистрирует команду, говорит через TTS, вешает хоткей и слушает событие — всё через SDK.
- [ ] Вызов без выданного разрешения отклоняется с понятной ошибкой и попадает в аудит.
- [ ] `execute_action` не обходит проверку прав и подтверждение опасных действий.
- [ ] Sandboxed-плагин работает через IPC, его падение не задевает приложение, процесс поднимается заново.
- [ ] Зависший хук прерывается по таймауту, плагин помечается неотзывчивым.
- [ ] Шаблон плагина устанавливается и работает без правок; документация SDK генерируется из кода.
