# Задача 05 — Воркеры и IPC

**Этап:** A — Фундамент | **Зависит от:** 04 | **Разделы ТЗ:** 1.2, 12, 14

## Цель
Инфраструктура изолированных процессов для аудио, STT, TTS и LLM: запуск, протокол обмена, health-check, авто-перезапуск.

## Что сделать
1. `workers/protocol.py`: типизированные сообщения запрос/ответ (`Request(id, method, params)`, `Response(id, ok, payload, error)`, `Event(kind, payload)`), сериализация (pickle для локального IPC, с оговоркой о доверенности канала), версия протокола.
2. `workers/base.py`: базовый класс воркера — цикл чтения команд, диспетчер методов, обработка ошибок с отправкой `Response(ok=False)`, heartbeat раз в N секунд, graceful stop по сигналу, установка приоритета процесса из конфига.
3. `workers/manager.py` — `WorkerManager`:
   - Запуск воркера по спецификации (тип, entrypoint, конфиг).
   - Дуплексный канал `multiprocessing.connection.Pipe`, отдельный поток-читатель на воркера, публикация входящих событий в event bus.
   - Async/future-подобный API: `call(worker, method, params, timeout)` возвращает future.
   - Health-check по heartbeat, детект зависания и краша.
   - Авто-перезапуск за ~1 сек с экспоненциальной задержкой при повторных падениях, лимит попыток, публикация `WorkerCrashed` / `WorkerRestarted`.
   - Передача больших аудио-буферов через `multiprocessing.shared_memory`, а не через pipe.
   - Корректное завершение всех воркеров при shutdown.
4. `workers/registry.py`: описание типов воркеров (`audio`, `stt`, `tts`, `llm`), какие из них поднимать по текущему конфигу. Режим экономии: при онлайн-движках локальные воркеры не стартуют или паузятся.
5. Тесты: эхо-воркер (запуск, call/response, timeout), убийство процесса → авто-перезапуск, передача буфера через shared memory, shutdown без зависших процессов.

## Осторожно
- Windows использует spawn: воркер не наследует состояние, всё нужное передаётся в аргументах старта. Проверено: `spawn` и `shared_memory` работают и в песочнице чата (процесс поднимается за ~0.4 с), поэтому тесты пишутся на настоящих процессах. Никакого «потокового транспорта для тестов» делать не нужно — подделка не ловит именно те ошибки, ради которых всё затевалось: непиклящиеся объекты, глобальное состояние, не переживающее spawn, и гонки при завершении.
- Не импортировать PySide6 в воркерах.
- Не оставлять сирот: воркеры должны умирать вместе с родителем (job object или сторожевой таймер по heartbeat родителя).
- `shared_memory` на Linux оставляет запись в `resource_tracker` и сыплет предупреждениями при выходе; в проекте `filterwarnings = ["error"]`, так что предупреждение превратится в упавший тест. Снимать регистрацию явно.

## Готово когда
- [ ] Тестовый воркер запускается, отвечает на call, корректно останавливается.
- [ ] Принудительное убийство процесса приводит к перезапуску < 2 сек и событиям в шине.
- [ ] Аудио-буфер 10 секунд передаётся через shared memory без заметной задержки.
- [ ] Тесты проходят на настоящих процессах (`spawn`), а не на потоках-заглушках.
- [ ] После выхода из приложения в диспетчере задач не остаётся процессов. — **проверяет CI на windows-раннере**, отдельным тестом на отсутствие живых дочерних PID после `stop()`.
