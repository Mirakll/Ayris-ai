# Задача 61 — Абстракция LLM и облачные провайдеры

**Этап:** H — LLM | **Зависит от:** 05 | **Разделы ТЗ:** 5.3

## Цель
Единая абстракция LLM-клиента со стримингом токенов и шесть облачных провайдеров за ней, плюс LLM-воркер, который не блокирует главный процесс.

## Что сделать
1. `nlu/llm/base.py`: ABC `LLMClient` — `chat(messages, system, tools=None, stream=True)`, отдающий поток дельт (`TokenDelta`, `ToolCallDelta`, `Usage`, `Done`), плюс `list_models()` и `check_credentials()`. Типы `Message(role, content)`, `ToolSpec`, `LLMResult` — dataclass'ы, не словари. Флаги поддержки стриминга и tool calling у каждой реализации. Добавление провайдера = новый файл, вызывающий код не меняется.
2. Реализации на httpx, один файл на провайдера: OpenAI (GPT-4o, 4o-mini), Anthropic (Claude 3.5 Sonnet/Haiku), OpenRouter, YandexGPT, GigaChat (OAuth-токен с автообновлением), DeepSeek. Ключи API — только в `keyring` (Windows Credential Manager), в `config.toml` хранится провайдер, модель и id записи, но не сам ключ.
3. Стриминг для быстрого старта TTS: сборка дельт в законченные предложения (аккуратно с сокращениями и числами) и публикация `LLMSentenceReady` по мере готовности, чтобы озвучка начиналась до конца генерации. Отмена посреди стрима закрывает соединение и останавливает TTS.
4. Надёжность: раздельные таймауты connect/read, ретраи с экспоненциальным backoff и jitter только на 429/5xx/сетевых, без ретраев на 4xx. Типизированные исключения в `core/errors.py` для квоты, авторизации, переполнения контекста, отмены — каждое с понятным русским сообщением для UI вместо трейсбека.
5. `nlu/llm/usage.py`: токены из ответа API, эвристическая оценка там, где их нет; таблица цен на провайдера и модель; стоимость запроса и накопленная за сессию, событие `LLMUsage` для DevTools и вкладки ИИ.
6. `workers/llm_worker.py`: воркер на инфраструктуре задачи 05 — методы `chat`, `cancel`, `list_models`, `check_key`; дельты уходят событиями, а не одним ответом; краш воркера обрабатывается менеджером без потери GUI.
7. Тесты на моках httpx для каждого провайдера: успешный стрим, 401, 429 с ретраем, обрыв соединения посреди стрима, сборка предложений из дельт, подсчёт стоимости.

## Осторожно
- `keyring` — новая зависимость, добавить в `pyproject.toml` и проверить, что она работает в собранном Nuitka-бинарнике.
- Ключи не должны попадать в логи, события и сообщения об ошибках — маскировать при любом выводе.
- Zero telemetry: ни одного запроса к провайдеру без явного действия пользователя, включая «проверку ключа».
- Стрим нельзя копить в буфер целиком — иначе теряется весь смысл раннего старта TTS.

## Готово когда
- [ ] Смена провайдера в конфиге не требует правок вызывающего кода.
- [ ] Первое предложение ответа уходит в TTS до конца генерации, отмена глушит и стрим, и озвучку.
- [ ] Неверный ключ и исчерпанная квота дают понятное сообщение в UI, воркер остаётся живым.
- [ ] Обрыв сети посреди стрима не роняет пайплайн: либо ретрай, либо корректная ошибка.
- [ ] В логе после запроса видны модель, токены и стоимость.
- [ ] Тесты на моках зелёные, mypy strict проходит.
