# Задача 41 — Логирование и аудит

**Этап:** F — Хоткеи и интеграция ядра | **Зависит от:** 03 | **Разделы ТЗ:** 11, 15

## Цель
Полноценное логирование с ротацией и отдельным каналом лога пайплайна, аудит всех выполненных команд в БД и экспорт для баг-репортов с автоматической вычисткой секретов.

## Уже готово, переписывать не надо
Половину этой задачи довезли задачи 03, 07 и 19 — потому что без логов не отлаживались
воркеры, а без аудита не сдавались опасные действия. Начни с чтения этого кода:

- **`utils/logger.py`** — `DailySizedRotatingFileHandler` (ротация по дате и по размеру,
  `purge_expired()`, `MAX_BYTES`, `BACKUP_DAYS`), `setup_logging(level, console, log_dir)`
  (идемпотентна, повторный вызов только меняет уровень через `_apply_level`),
  `get_logger`, `get_pipeline_logger`, `shutdown_logging`, префиксы `MAIN_LOG_PREFIX` и
  `PIPELINE_LOG_PREFIX`. **И готовая вычистка секретов:** `guard_secret(value)`,
  `forget_secret(value)`, `redact(text)`, `SecretFilter`, `SECRET_PLACEHOLDER`,
  `guarded_secret_count()`.
- **Логи воркеров.** Схема уже другая, чем предполагал этот файл, и она работает: каждый
  воркер пишет свой `worker_<имя>_YYYYMMDD.log` тем же обработчиком, а записи от
  `log_forward_level` и выше уходят в главный процесс по существующему пайпу
  (`_PipeLogHandler` в `workers/base.py`), где `workers/manager.py` публикует их в шину как
  `LogLine`. Один файл на несколько процессов не пишется вообще — **`QueueHandler` с
  слушателем не заводить**, это замена работающего механизма на другой такой же.
- **Канал пайплайна и сквозной id.** `core/pipeline.py` пишет строку в
  `get_pipeline_logger()` с `extra={"request_id": ...}`, `core/pipeline_trace.py` содержит
  `Stage` с русскими метками, `StageTiming(stage, duration_ms, ok, detail, describe, as_json)`
  и `PipelineTrace` с `stage()`, `record()`, `finish()`, `total_ms`, `duration_of()`,
  `log_line()`, `as_json()`, `to_history()`. `request_id` есть полем у событий шины и
  параметром у `registry.execute/aexecute/undo`.
- **Аудит.** Пишет его реестр действий: строка со временем, именем действия,
  замаскированными параметрами, результатом, длительностью, `require_admin`, `elevated`,
  `confirmed`. Есть `AuditEntry` и `AuditRepository` (`add`, `recent(limit, elevated_only=)`,
  `count`, `delete_older_than`, `clear`). **Второго писателя аудита не создавать.**
- **Маскирование по схеме** — `secret_fields(model)` и `mask_params(params)` в
  `actions/base.py`, реестр применяет их до записи.
- **Конфиг** — секция `[devtools]`: `log_level`, `console_log`, `pipeline_log`,
  `log_retention_days`, `log_max_mb`, `repl_enabled`, `text_input`. Новой секции не надо.

## Что сделать
1. Переключение уровня на лету, включая отдельный модуль: сейчас `setup_logging` меняет
   уровень всему дереву сразу, а «включить DEBUG только для `audio.vad`» нечем. Добавить
   явное API (`set_level(level)`, `set_module_level(name, level)`, сброс к общему) и вернуть
   текущее состояние для UI. Заодно **подключить настройки к обработчику**:
   `devtools.log_max_mb` и `devtools.log_retention_days` объявлены в конфиге, но до
   `DailySizedRotatingFileHandler` не доходят — он работает на константах `MAX_BYTES` и
   `BACKUP_DAYS`. Это баг, а не задел: настройка, которая ничего не меняет, хуже, чем её
   отсутствие.
2. Канал лога пайплайна: `request_id` должен быть виден в файле — проверить формат
   обработчика и добавить поле, чтобы одну цепочку можно было выбрать `grep` по id. Всё
   остальное для «одна запись на запрос» уже есть в `PipelineTrace`; если чего-то не хватает
   для таблицы стадий в DevTools, дописывать в `pipeline_trace.py`, а не заводить рядом
   второй формат. Отдельный `utils/pipeline_log.py` создавать не нужно: канал есть, трейс
   есть; если он всё же появляется — только как тонкий приёмник, без своей модели стадий.
3. Кольцевой буфер последних N строк в памяти (размер из конфига — добавить поле в
   `[devtools]`) для мгновенного показа в DevTools без чтения файла, с фильтром по уровню и
   по модулю. Это настоящая новая работа: буфера в проекте нет.
4. Публикация `LogLine` в шину для главного процесса: сейчас событие публикуется только для
   строк, пришедших от воркеров. Добавить обработчик, который отправляет туда же записи
   главного процесса, и добавить в событие `LogLine` поле `request_id` — **аддитивно**, с
   значением по умолчанию, потому что на событии уже стоят подписчики. Публикация не должна
   тормозить логирование: неблокирующая очередь, при переполнении — отбрасывание со
   счётчиком (счётчик показывать в DevTools, иначе потеря строк выглядит как их отсутствие).
5. Выборки аудита для UI: `core/audit.py` — **только чтение** поверх `AuditRepository`
   (фильтры по времени, команде, действию, результату, флагам; страницы для таблицы;
   агрегаты для «что чаще всего запускалось»). Если для фильтров нужны индексы или колонка
   (например, источник триггера — его в строке нет) — миграция вперёд плюс заполнение из
   реестра, там же, где строка уже собирается.
6. `utils/redaction.py`: регулярные выражения для типовых секретов (Bearer-токены, ключи
   `sk-…`, длинные base64, номера карт) и повторный проход по готовому тексту — то, что
   нельзя выразить ни схемой действия, ни списком известных значений. Поверх уже
   существующего: значения, которые известны точно, регистрируются через `guard_secret` и
   вычищаются `SecretFilter` автоматически; поля со схемой закрывает `mask_params`. Если
   задача 27 уже создала этот модуль минимальным — расширить, не переписать.
7. Экспорт для баг-репорта: сборка архива с логами за N дней (включая файлы воркеров),
   аудитом, конфигом без секретов, версиями приложения и зависимостей, сведениями об ОС и
   аудио-устройствах; повторный проход вычистки секретов по всему содержимому перед
   упаковкой; отчёт пользователю, что именно попало в архив, и открытие папки с ним.
8. Тесты: ротация по размеру и по дате (сейчас не проверена ничем — `DailySizedRotatingFileHandler`
   в тестах не встречается, так что это первое покрытие, а не дополнение), лимиты из конфига
   доходят до обработчика, переключение уровня на лету и по модулю, `request_id` в строке
   пайплайна и в `LogLine`, кольцевой буфер с фильтрами и счётчиком отброшенных, выборки
   аудита, маскирование секретов в логе и в аудите, экспортированный архив не содержит
   ключей (по фикстуре с подставленным секретом).

## Осторожно
- Несколько процессов, пишущих в один файл на Windows, приводят к порче лога и блокировкам.
  В проекте этого и нет: у каждого воркера свой файл, наверх идёт пайп. Не сводить их в один
  файл «для удобства».
- `print()` в проекте не допускается — весь вывод через логгер (проверить и поправить
  существующий код).
- Zero telemetry: экспорт баг-репорта только в локальный файл, никакой автоматической
  отправки.
- Уровень DEBUG не должен писать сырой звук, тексты паролей и полные тела HTTP-запросов.
- Ротация не должна терять записи при работающем приложении и при смене даты в полночь.
- Ротация на Windows ведёт себя не так, как в песочнице: файл, открытый другим процессом,
  нельзя переименовать, и обработчик молча теряет запись. Логику ротации проверять везде, а
  тест с несколькими живыми писателями закрывать `pytest.mark.skipif(sys.platform != "win32")` —
  толк от него есть именно на windows-раннере.
- `LogLine` уже используется: поле добавлять со значением по умолчанию и не менять порядок
  существующих, иначе поедут позиционные конструкции у подписчиков.
- Сборка баг-репорта перечисляет аудио-устройства и сведения об ОС: на раннере CI устройств
  нет, и функция должна отдавать пустой список, а не падать. Иначе тест экспорта краснеет
  там, где ошибки в коде нет.
- Вычистку секретов нельзя проверять на глаз — нужен отдельный тест: прогнать через логгер и
  через запись в `audit` строки с паролем, номером карты и содержимым буфера обмена, затем
  прочитать файл лога и таблицу и убедиться, что подстановок там нет ни в каком виде. Тот же
  тест повторить для экспорта баг-репорта, распаковав собранный архив и поискав те же строки
  во всём содержимом, включая конфиг. Это чистая логика, она проверяется и в песочнице, и в CI.
- Сами секреты в проекте не хранятся: они живут в Windows Credential Manager через `keyring`,
  а в `config.toml` лежит только `credential_ref`. Если в конфиг попало значение, а не
  ссылка, — это ошибка, и тест экспорта должен её ловить.
