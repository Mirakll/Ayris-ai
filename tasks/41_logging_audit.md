# Задача 41 — Логирование и аудит

**Этап:** F — Хоткеи и интеграция ядра | **Зависит от:** 03 | **Разделы ТЗ:** 11, 15

## Цель
Полноценное логирование с ротацией и отдельным каналом лога пайплайна, аудит всех выполненных команд в БД и экспорт для баг-репортов с автоматической вычисткой секретов.

## Что сделать
1. Расширение `utils/logger.py`: уровни DEBUG/INFO/WARNING/ERROR с переключением на лету без рестарта (в том числе на отдельный модуль), файл `%APPDATA%\Ayris\logs\ayris_YYYYMMDD.log` через `paths.py`, ротация по размеру 10 МБ и по дате с хранением 7 дней, безопасная запись из нескольких процессов (`QueueHandler` + слушатель в главном процессе, воркеры пишут в очередь, а не в тот же файл).
2. Канал лога пайплайна: отдельный логгер и формат для цепочки `STT raw → NLU intent → Action → Result` с таймингами каждой стадии в мс, сквозным `request_id` от wake word до озвученного ответа, итоговой суммой времени. Один запрос — одна связная запись, которую можно показать в DevTools как таблицу стадий.
3. Кольцевой буфер последних N строк в памяти (размер из конфига) для мгновенного показа в DevTools без чтения файла, с фильтром по уровню и по модулю.
4. Публикация `LogLine` в event bus (уровень, модуль, время, текст, `request_id`) — DevTools и оверлей подписываются на события, а не читают файл. Публикация не должна тормозить логирование: неблокирующая очередь, при переполнении — отбрасывание с счётчиком.
5. Аудит: запись каждой выполненной команды в таблицу `audit` — время, имя команды и действия, параметры, источник триггера, результат, длительность, флаги `require_admin` / `elevated`, исход подтверждения (задача 40). Репозиторий с выборками по времени, команде и результату для UI.
6. Фильтрация чувствительных значений перед записью: параметры с признаком `secret` в схеме действия (задача 19), пароли, API-ключи, токены, содержимое буфера обмена, тексты автозаполнения. Единая функция маскирования, применяемая и к логу, и к аудиту, плюс набор регулярных выражений для типовых секретов (Bearer-токены, ключи вида `sk-...`).
7. Экспорт для баг-репорта: сборка архива с логами за N дней, аудитом, конфигом без секретов, версиями приложения и зависимостей, сведениями об ОС и аудио-устройствах; повторный проход вычистки секретов по всему содержимому перед упаковкой; отчёт пользователю, что именно попало в архив, и открытие папки с ним.
8. Тесты: ротация по размеру и по дате; переключение уровня на лету; корректный порядок и тайминги стадий пайплайна с одним `request_id`; запись и выборка аудита; маскирование секретных параметров в логе и в аудите; экспортированный архив не содержит ключей (проверка по фикстуре с подставленным секретом).

## Осторожно
- Несколько процессов, пишущих в один файл на Windows, приводят к порче лога и блокировкам: только очередь и один писатель.
- `print()` в проекте не допускается — весь вывод через логгер (проверить и поправить существующий код).
- Zero telemetry: экспорт баг-репорта только в локальный файл, никакой автоматической отправки.
- Уровень DEBUG не должен писать сырой звук, тексты паролей и полные тела HTTP-запросов.
- Ротация не должна терять записи при работающем приложении и при смене даты в полночь.
- Ротация на Windows ведёт себя не так, как в песочнице: файл, открытый другим процессом, нельзя переименовать, и обработчик молча теряет запись. Логику ротации проверять везде, а тест с несколькими живыми писателями закрывать `pytest.mark.skipif(sys.platform != "win32")` — толк от него есть именно на windows-раннере.
- Сборка баг-репорта перечисляет аудио-устройства и сведения об ОС: на раннере CI устройств нет, и функция должна отдавать пустой список, а не падать. Иначе тест экспорта краснеет там, где ошибки в коде нет.
- Вычистку секретов нельзя проверять на глаз — нужен отдельный тест: прогнать через логгер и через запись в `audit` строки с паролем, номером карты и содержимым буфера обмена, затем прочитать файл лога и таблицу и убедиться, что подстановок там нет ни в каком виде. Тот же тест повторить для экспорта баг-репорта, распаковав собранный архив и поискав те же строки во всём содержимом, включая конфиг. Это чистая логика, она проверяется и в песочнице, и в CI.
- Сами секреты в проекте не хранятся: они живут в Windows Credential Manager через `keyring`, а в `config.toml` лежит только `credential_ref`. Если в конфиг попало значение, а не ссылка, — это ошибка, и тест экспорта должен её ловить.

## Готово когда
- [ ] Логи пишутся в файл с ротацией 10 МБ / 7 дней, воркеры не портят файл — **проверяет CI на windows-раннере**
- [ ] Уровень логирования меняется на лету, включая отдельные модули.
- [ ] Лог пайплайна показывает стадии `STT → NLU → Action → Result` с таймингами и общим `request_id`.
- [ ] Буфер последних строк отдаётся мгновенно, события `LogLine` приходят в шину.
- [ ] Каждая выполненная команда есть в аудите с флагами admin/elevated и результатом.
- [ ] Секреты замаскированы и в логе, и в аудите, и в экспортированном архиве.
- [ ] Тесты, ruff, black и mypy зелёные.
