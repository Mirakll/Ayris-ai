# Задача 24 — Сеть и питание

**Этап:** D — Системные действия | **Зависит от:** 19 | **Разделы ТЗ:** 6 (Сеть/Питание), 11

## Цель
Управление Wi-Fi и Bluetooth плюс действия питания (сон, гибернация, перезагрузка, выключение, блокировка) с обязательным подтверждением опасных операций.

## Что сделать
1. `actions/system/network.py`: Wi-Fi через WinRT (`Windows.Devices.Radios.Radio`) с фоллбеком на `netsh wlan` — включение/выключение адаптера, список доступных сетей (SSID, уровень сигнала, тип защиты, флаг «сохранённый профиль»), подключение к сети по сохранённому профилю и с паролем. Действия `SetWifi`, `ListWifi`, `ConnectWifi`.
2. Bluetooth: включение/выключение радио через ту же `Radio` API, перечисление сопряжённых и подключённых устройств (имя, тип, статус) через `Windows.Devices.Enumeration`. Действие `SetBluetooth`. Парсинг вывода `netsh` вынести в отдельные чистые функции — их и тестировать, локаль вывода `netsh` зависит от языка системы, поэтому не полагаться на русские подписи полей.
3. `actions/system/power.py`: сон и гибернация через `SetSuspendState`, перезагрузка и выключение через `ExitWindowsEx` / `InitiateSystemShutdownExW` (с включением привилегии `SE_SHUTDOWN_NAME` для текущего процесса), блокировка через `LockWorkStation`. Действия `PowerAction` (параметр-enum: `sleep`/`hibernate`/`reboot`/`shutdown`/`logoff`) и `LockWorkstation`. Поддержка отложенного выполнения (задержка в секундах) и отмены запланированного выключения.
4. Метаданные безопасности: все действия питания кроме блокировки регистрируются с `is_dangerous=True`, `SetWifi`/`SetBluetooth`/`ConnectWifi` — с `require_admin` там, где повышение реально требуется. Реестр (задача 19) перед выполнением опасного действия обращается к механизму подтверждения из задачи 40 (голос/ПИН/Windows Hello); при отказе — `ActionError` без выполнения.
5. Проверка прав: определение, запущен ли процесс с повышением, и запрос повышения через UAC-перезапуск вспомогательного процесса (`ShellExecuteW` с `runas`) вместо повышения всего помощника. Хелперы в `utils/admin.py`.
6. Общие требования: сохранение пароля Wi-Fi только в keyring, никогда в логи и аудит (пометка параметра секретным по схеме из задачи 19); все действия питания пишутся в `audit` с отметкой подтверждения; понятные русские сообщения при отсутствии адаптера или выключенном радио.
7. Тесты: парсеры вывода `netsh` на фикстурах (русская и английская локаль), enum и валидация параметров `PowerAction`, обязательность подтверждения для опасных действий (мок механизма подтверждения), маскирование пароля, поведение при отсутствии Wi-Fi/Bluetooth адаптера.

`src/ayris/actions/system/network.py`, `src/ayris/actions/system/power.py`, `src/ayris/utils/admin.py`, `tests/unit/test_network.py`, `tests/unit/test_power.py`

## Осторожно
- Реальные вызовы питания в тестах и при отладке недопустимы — обязателен dry-run режим и мок на уровне бэкенда.
- `ExitWindowsEx` без включённой привилегии `SE_SHUTDOWN_NAME` возвращает ошибку доступа — привилегию нужно включать явно для потока.
- Гибернация может быть отключена в системе (`powercfg /a`) — проверять доступность до попытки и сообщать причину.
- Вывод `netsh` локализован и различается между сборками: парсить по структуре, а не по подписям на русском.
- Radio API требует согласия пользователя (`RequestAccessAsync`) — обрабатывать отказ.

## Готово когда
- [ ] Wi-Fi включается/выключается, список сетей приходит типизированным, подключение по сохранённому профилю работает.
- [ ] Bluetooth переключается, список сопряжённых устройств отдаётся.
- [ ] Блокировка экрана работает; сон/перезагрузка/выключение выполняются только после подтверждения.
- [ ] Без подтверждения опасное действие возвращает ошибку и ничего не делает.
- [ ] Пароль Wi-Fi отсутствует в логах и в таблице `audit`.
- [ ] Тесты на парсерах и на обязательности подтверждения зелёные.
