# Задача 09 — Wake word

**Этап:** B — Аудио и речь | **Зависит от:** 08 | **Разделы ТЗ:** 2

## Цель
Активация помощника по ключевому слову «Айрис» и пользовательским вариантам, работающая в аудио-воркере параллельно с VAD, плюс точка входа для Push-to-Talk.

## Что сделать
1. `audio/wake_word/base.py`: ABC `WakeWordEngine` — `load(model_spec)`, `process(frame) -> WakeDetection | None`, `unload()`, свойства требуемой частоты дискретизации и размера кадра. Dataclass `WakeDetection(phrase, score, timestamp)` и `WakePhrase(text, sensitivity, engine_model)`.
2. Реализации движков: `openwakeword.py` (основной, бесплатный), `porcupine.py` (pvporcupine, ключ из keyring, опциональная зависимость), `vosk_kws.py` (KWS по грамматике из списка фраз). Отсутствие библиотеки — понятная ошибка при выборе движка, а не падение импорта.
3. Неограниченный список пользовательских вариантов слова, у каждого своя чувствительность 0.0–1.0. Порог сравнивается с score конкретной фразы, а не общий на движок. Добавление/удаление вариантов на лету без перезапуска воркера.
4. Debounce: после срабатывания игнорировать детекции 1.5–2 сек (значение из конфига), отдельно на каждую фразу и глобально. Публикация `WakeWordDetected(phrase, score)` в event bus.
5. Встроить детектор в аудио-воркер рядом с VAD: один поток кадров кормит и VAD, и wake word, без второго открытия устройства. После срабатывания — переход к записи фразы сегментатором из задачи 08.
6. Метрика ложных срабатываний: счётчик детекций, отвергнутых по порогу и по debounce, накопление за сессию, публикация для UI и лога — чтобы можно было подбирать чувствительность.
7. Push-to-Talk как альтернативный путь активации: метод `trigger_manual(source)` в аудио-воркере, публикующий `WakeWordDetected(phrase="<ptt>")`. Сам глобальный хоткей — задача 37, здесь только точка входа и режим микрофона (Always / PTT / Hybrid) из конфига.
8. Тесты на WAV-фикстурах: запись со словом «Айрис» (срабатывает), запись без него и похожая по звучанию фраза (не срабатывает), двойное произнесение внутри окна debounce (одно событие).

## Осторожно
- Движки требуют строго свою частоту и размер кадра: 16 кГц у всех, но openWakeWord ждёт блоки по 1280 сэмплов (80 мс), а Porcupine — ровно `frame_length` = 512. Ресемплинг и нарезку кадров делать в менеджере, а не в каждом движке.
- Porcupine бесплатен только для личного использования и требует access key — не тащить его в дефолтную конфигурацию.
- Не запускать инференс в потоке колбэка sounddevice: очередь кадров и отдельный поток обработки, иначе дропы аудио.
- Debounce считать по времени аудио, а не по wall-clock, иначе на нагруженной машине окно поедет.
- `openwakeword==0.6.0` уже в `pyproject.toml`; ту же версию надо добавить в `requirements-ci.txt`, иначе упадёт `tests/unit/test_packaging.py` — он сравнивает пины между файлами. Библиотека тянет tflite/onnxruntime, и если колесо не встанет на раннере, зависимость в `requirements-ci.txt` не добавляется, а импорт движка делается отложенным, чтобы сбор тестов в CI не падал на верхнеуровневом `import`.
- Веса движков в репозиторий не кладутся, так что тесты на настоящем движке помечаются `@pytest.mark.hardware` и в CI не запускаются. Логика менеджера (порог на фразу, debounce, добавление вариантов) должна проверяться на фейковом движке, отдающем заданные score, — иначе в CI от этой задачи не останется ни одного зелёного теста.

## Готово когда
- [ ] Фикстура со словом «Айрис» даёт ровно одно `WakeWordDetected`, фикстура без него — ноль. — **проверяешь ты руками**: нужна скачанная модель openWakeWord, в CI её нет
- [ ] Изменение чувствительности варианта меняет срабатывание без перезапуска воркера.
- [ ] Двойное произнесение в пределах 1.5 сек публикует одно событие.
- [ ] Wake word и VAD работают на одном потоке кадров, без дропов на 60-секундном прогоне. — **проверяешь ты руками**: нужен микрофон и минута живого прогона, потом посмотреть счётчик дропов
- [ ] `trigger_manual` даёт тот же путь активации, что и голосовое срабатывание.
- [ ] Счётчик ложных срабатываний доступен из UI-метрик.
