# Задача 15 — Matcher exact/fuzzy/regex

**Этап:** C — NLU и пайплайн | **Зависит от:** 03 | **Разделы ТЗ:** 5.2

## Цель
Сопоставление распознанной фразы с заготовленными командами: точное совпадение, fuzzy по Levenshtein и regex с именованными группами, с приоритетами и разрешением конфликтов.

## Что сделать
1. `nlu/normalize.py`: нормализация текста перед матчингом — приведение регистра, ё→е, снятие пунктуации и лишних пробелов, удаление обращения «айрис» в начале фразы, числительные словами в цифры («пятьдесят» → «50»). Функция чистая и переиспользуемая, применяется и к триггерам, и к входному тексту одним и тем же путём.
2. `nlu/matcher.py`: `Matcher` с тремя стратегиями. Exact — по нормализованной строке через словарь. Fuzzy — Levenshtein (rapidfuzz, если он в зависимостях, иначе своя реализация) с настраиваемым порогом схожести, порог задаётся глобально и переопределяется на триггер. Regex — компиляция шаблона с именованными группами, группы уходят в слоты (задача 16).
3. Dataclass'ы: `Trigger(id, command_id, kind, pattern, fuzzy, threshold, weight, priority, enabled)` и `MatchResult(command_id, trigger_id, score, kind, raw_groups, normalized_text)`. Множественные триггеры на одну команду с индивидуальными весами и приоритетами.
4. Разрешение конфликтов при нескольких совпадениях: сортировка по приоритету команды → весу триггера → score → типу совпадения (exact > regex > fuzzy) → длине совпавшего шаблона (более специфичный выигрывает). Детерминированный порядок при равенстве, метод `match_all()` для отладки и `match()` для одного лучшего результата.
5. `nlu/index.py`: индекс триггеров в памяти — словарь для exact, список скомпилированных regex, структура для fuzzy с предфильтром (по длине и первым символам/n-граммам, чтобы не гонять Levenshtein по всем 1000+ триггерам). Перестройка индекса при изменении команд: подписка на события изменения команд из БД, инкрементальное обновление одной команды вместо полной перестройки, потокобезопасность (матчинг может идти во время обновления).
6. Производительность: матчинг по 1000+ триггерам укладывается в единицы миллисекунд. Бенчмарк-тест с генерацией 1000 триггеров и замером времени, порог в тесте с запасом.
7. Тесты: точное совпадение с учётом нормализации, fuzzy на опечатках STT («открой браузир»), отсечение по порогу, regex с именованными группами, приоритеты и веса при конфликте, отключённые триггеры игнорируются, инкрементальная перестройка индекса, бенчмарк.

## Осторожно
- Fuzzy на короткие фразы даёт мусор: минимальная длина для fuzzy и порог, растущий с укорочением фразы, иначе «да» совпадёт с половиной библиотеки.
- Нормализация числительных не должна ломать regex-триггеры, где ожидаются слова — regex матчить по тексту до нормализации чисел (хранить оба варианта в `MatchResult`).
- Компилировать regex один раз при построении индекса; битый пользовательский шаблон не должен ронять матчинг — валидация при сохранении команды и пропуск с записью в лог.
- Матчинг вызывается из пайплайна на каждой фразе — никаких обращений к БД внутри `match()`, только индекс в памяти.

## Готово когда
- [ ] «Айрис, открой браузер» и «открой браузер» матчатся на один триггер.
- [ ] Опечатка STT в одном слове ловится fuzzy, а слишком далёкая фраза отсекается порогом.
- [ ] Regex-триггер отдаёт именованные группы в `MatchResult.raw_groups`.
- [ ] При двух совпадениях выигрывает команда с более высоким приоритетом, порядок детерминирован.
- [ ] Изменение одной команды обновляет индекс без полной перестройки и без гонок.
- [ ] Бенчмарк на 1000+ триггерах проходит в пределах заданного лимита времени.
