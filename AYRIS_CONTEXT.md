# AYRIS — общий контекст проекта

Прикрепляй этот файл к КАЖДОМУ новому чату вместе с `AYRIS_SPEC.md` и файлом конкретной задачи из `tasks/`.

## Что это
Ayris (Айрис) — голосовой помощник для Windows 11. Русскоязычный UI, офлайн-first с облачными фоллбеками, движок макросов в стиле VoiceAttack, система плагинов, оверлей с анимированной сферой из точек.

## Стек (не менять без причины)
- Python 3.11+, PySide6 (Qt 6) для GUI, QSS для стилей.
- pydantic + pydantic-settings для конфигурации, `config.toml` как формат.
- sqlite3 (stdlib) для команд, переменных, истории, таймеров, аудита.
- multiprocessing + `multiprocessing.connection` для воркеров STT/TTS/LLM/Audio.
- Сборка: Nuitka, инсталлер Inno Setup.
- Качество: ruff, mypy (strict), black, pytest, pre-commit.

## Инварианты архитектуры
1. **Main process** — GUI, event bus, БД, настройки, NLU, макросы, плагины. **Worker processes** — audio capture+VAD+wake word, STT, TTS, LLM. Краш воркера не должен ронять GUI.
2. **Ничего не блокирует UI-поток.** Любая тяжёлая операция — воркер, `QThread` или async.
3. **Общение через event bus.** Модули не импортируют друг друга напрямую там, где хватает события. Event bus типизирован (dataclass-события).
4. **Движки — за абстракцией.** Каждый STT/TTS/WakeWord/LLM движок реализует общий ABC (`transcribe()`, `synthesize()`, ...). Добавление движка = новый файл, без правок вызывающего кода.
5. **Действия — через реестр.** Любое системное действие регистрируется в `actions/registry.py` со схемой параметров. Макросы и NLU вызывают действия только через реестр.
6. **Пути только через `core/paths.py`.** Никаких хардкодов `%APPDATA%` по коду.
7. **Zero telemetry.** Никаких исходящих соединений без явного действия пользователя.

## Git
Репозиторий уже инициализирован, ветка `main`, первый коммит содержит этапы A–C. Один коммит на задачу, сообщение — `NN: что сделано`. Не делай `git push --force`, не переписывай чужие коммиты: над проектом параллельно работают несколько чатов, и твоя ветка — общая.

## Структура репозитория
Следуй разделу 24 ТЗ (`src/ayris/{core,audio,nlu,actions,plugins,gui,onboarding,utils}`). Каждый модуль — отдельный файл. Не создавай файлы вне этой структуры без нужды.

## Конвенции кода
- Идентификаторы, имена файлов, docstring'и — английский. Пользовательские строки в UI — русский.
- Полные type hints, mypy strict проходит. Dataclass'ы/pydantic-модели вместо словарей для структурированных данных.
- Комментарии только там, где логика неочевидна. Никаких заглушек `pass  # TODO` в сдаваемом коде — только рабочий код.
- Логирование через `utils/logger.py`, никаких `print()`.
- Ошибки: свои исключения в `core/errors.py`, наверх пробрасывается типизированное исключение, не голый `Exception`.
- Все внешние вызовы (сеть, аудио-устройства, WinAPI) обёрнуты в обработку ошибок с логом и понятным сообщением для пользователя.

## Конвенции данных
- Схема БД — миграции с версией в таблице `schema_version`. Не ломать существующие таблицы, только миграция вперёд.
- Формат экспорта команд — `.ayris` (JSON) с полем `schema_version`.
- Настройки: секции в `config.toml` соответствуют вкладкам настроек.

## Тема оформления
Тёмно-фиолетовая, футуристичная, минималистичная. Цветовые токены в одном месте (`resources/themes/`), никаких хардкодов цветов в виджетах. Оверлей: Topmost, не перехватывает фокус, per-monitor DPI aware.

## Правила работы в чате-задаче
1. Прочитай задачу целиком, затем нужные существующие файлы проекта — не переписывай то, что уже работает.
2. Меняй только файлы, перечисленные в задаче (плюс регистрация в реестре/индексе, если требуется).
3. Пиши рабочий код, а не каркас. Если что-то нельзя проверить без реального оборудования — скажи об этом прямо.
4. После кода прогони проверки одной командой: `bash scripts/check.sh` (~60 с; что именно она делает — в разделе «Как проверяется работа»). Оставляй проект в рабочем состоянии: красный `main` блокирует остальные 73 чата, а не только твой.
5. Если задача добавила runtime-зависимость — впиши её и в `pyproject.toml`, и в `requirements-ci.txt` с одинаковой версией, иначе CI не соберётся.
6. В конце отметь `[x]` для своей задачи в `AYRIS_ROADMAP.md` и одной строкой опиши, что появилось и какие интерфейсы теперь доступны следующим задачам.
7. Один коммит на задачу: `git add -A && git commit -m "NN: краткое описание"`. Перед `add` посмотри `git status` — не забирай в коммит чужую незакрытую задачу. После пуша дождись CI: `PYTHONIOENCODING=utf-8 _tools/venv/Scripts/python.exe scripts/ci_wait.py`.
8. Если задача упирается в непринятое решение — задай один вопрос, не изобретай архитектуру молча.

## Как проверяется работа
Проверки не сваливаются на пользователя: он не обязан уметь запускать линтеры. Всё, что можно проверить автоматически, должно проверяться автоматически — и одной командой, а не четырьмя.

**Три уровня.**
1. **В чате** — интерпретатор и инструменты лежат в самом проекте, сети не нужно.
   Всё проверяется одной командой, на любой из двух машин:

   ```bash
   bash scripts/check.sh          # всё: линтеры + тесты + окружение, ~60 с
   bash scripts/check.sh --lint   # ruff/black/mypy/пины/запуск, ~6 с
   bash scripts/check.sh tests/unit/test_нужный.py   # линтеры + один файл
   bash scripts/check.sh --fmt    # black переформатирует на месте
   ```

   Скрипт сам находит питон проекта (venv на Windows, портативный в песочнице),
   сам ставит `PYTHONIOENCODING=utf-8` — без него консоль в cp1251 падает на
   `UnicodeEncodeError` — и сам подставляет флаги, без которых в песочнице `mypy`
   падает на `PermissionError`, а `pytest` — на `RecursionError` при удалении tmp.
   Тесты идут в фон, линтеры — поверх них, поэтому ruff, black и mypy успевают
   закончиться внутри прогона бесплатно. Вывод — строка на проверку;
   разворачивается только упавшая.

   Кроме тестов проверяется то, чего тесты не видят: установленные версии
   совпадают с пинами (`scripts/verify_pins.py`), `python -m ayris --version`
   отвечает, секретов в трекаемых файлах нет. Чего прогон не покрыл — про это он
   говорит в конце сам, а не оставляет в «skipped».

   Чтобы не открывать соседние модули целиком ради их интерфейса, есть карта API:
   `scripts/map.py` (индекс модулей), `scripts/map.py <подсистема>` (сигнатуры), `--events`
   и `--errors` (шина событий и дерево исключений). Связи между модулями — граф `graphify`
   в `_tools/graph`, команды в `CLAUDE.md`.

   `spawn` и `shared_memory` работают в обеих средах, поэтому воркеры тестируются
   настоящими процессами, а не подделкой.
2. **CI на GitHub Actions** (`.github/workflows/ci.yml`) — источник истины. Пять джобов:
   линтеры, mypy и поиск секретов на ubuntu; тесты на **windows-latest** для Python 3.11
   и 3.12 (параллельно, `-n auto`); тесты на Linux — последовательно, это арбитр по гонкам;
   тесты на скачанных весах отдельным джобом. Именно здесь проверяется WinAPI-код,
   который в песочнице не запустить. Ждать прогон — `scripts/ci_wait.py`, а не `curl` руками.
3. **Руками у пользователя** — только то, что физически требует железа: микрофон, наушники, второй монитор, реальная громкость, яркость. Таких пунктов должно быть как можно меньше.

**Как писать тесты, чтобы это работало.**
- Тест, которому нужен настоящий микрофон или монитор, помечай `@pytest.mark.hardware`. Такие тесты исключены и в CI, и в локальном прогоне (`-m "not hardware"`), и это единственный способ не блокировать сборку: на машине без подключённого микрофона они падают COMError-ом, то есть красный цвет означал бы «микрофон отключён», а не «код сломан». Руками: `pytest -m hardware`.
- Тест, который утверждает что-то про время («уложился в N мс», «таймаут сработал»), помечай `@pytest.mark.slow`. Он пойдёт отдельным последовательным проходом: под `-n` такой тест делит ядро с семью процессами и становится броском монеты.
- Тест, которому нужны скачанные веса, — `@pytest.mark.models`, ходящий в чужой сервер — `@pytest.mark.network`. Первые идут отдельным джобом, вторые в CI не идут нигде (падение чужого сайта не должно красить сборку) и проверяются локальным прогоном.
- Тест, который работает только на Windows, скипай по `sys.platform`, а не маркером — тогда он сам оживёт на windows-раннере.
- Никаких `QApplication` с настоящим окном: в CI выставлен `QT_QPA_PLATFORM=offscreen`.
- WinAPI за `ctypes` изолируй так, чтобы логику можно было проверить подменой вызова, а не только на живой Windows.
- На каждый тест стоит потолок в 120 с (`pytest-timeout`): зависший тест обрывается со стеком, а не съедает джоб целиком.

**Формат.** `black` и `ruff` уже настроены на длину строки 100 и не спорят друг с другом. Хук перед коммитом ставится один раз (`pip install pre-commit && pre-commit install`) и зовёт `scripts/check.sh --lint` — тот же скрипт и тот же питон, что и вручную.
