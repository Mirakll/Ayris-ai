# AYRIS — общий контекст проекта

Прикрепляй этот файл к КАЖДОМУ новому чату вместе с `AYRIS_SPEC.md` и файлом конкретной задачи из `tasks/`.

## Что это
Ayris (Айрис) — голосовой помощник для Windows 11. Русскоязычный UI, офлайн-first с облачными фоллбеками, движок макросов в стиле VoiceAttack, система плагинов, оверлей с анимированной сферой из точек.

## Стек (не менять без причины)
- Python 3.11+, PySide6 (Qt 6) для GUI, QSS для стилей.
- pydantic + pydantic-settings для конфигурации, `config.toml` как формат.
- sqlite3 (stdlib) для команд, переменных, истории, таймеров, аудита.
- multiprocessing + `multiprocessing.connection` для воркеров STT/TTS/LLM/Audio.
- Сборка: Nuitka, инсталлер Inno Setup.
- Качество: ruff, mypy (strict), black, pytest, pre-commit.

## Инварианты архитектуры
1. **Main process** — GUI, event bus, БД, настройки, NLU, макросы, плагины. **Worker processes** — audio capture+VAD+wake word, STT, TTS, LLM. Краш воркера не должен ронять GUI.
2. **Ничего не блокирует UI-поток.** Любая тяжёлая операция — воркер, `QThread` или async.
3. **Общение через event bus.** Модули не импортируют друг друга напрямую там, где хватает события. Event bus типизирован (dataclass-события).
4. **Движки — за абстракцией.** Каждый STT/TTS/WakeWord/LLM движок реализует общий ABC (`transcribe()`, `synthesize()`, ...). Добавление движка = новый файл, без правок вызывающего кода.
5. **Действия — через реестр.** Любое системное действие регистрируется в `actions/registry.py` со схемой параметров. Макросы и NLU вызывают действия только через реестр.
6. **Пути только через `core/paths.py`.** Никаких хардкодов `%APPDATA%` по коду.
7. **Zero telemetry.** Никаких исходящих соединений без явного действия пользователя.

## Структура репозитория
Следуй разделу 24 ТЗ (`src/ayris/{core,audio,nlu,actions,plugins,gui,onboarding,utils}`). Каждый модуль — отдельный файл. Не создавай файлы вне этой структуры без нужды.

## Конвенции кода
- Идентификаторы, имена файлов, docstring'и — английский. Пользовательские строки в UI — русский.
- Полные type hints, mypy strict проходит. Dataclass'ы/pydantic-модели вместо словарей для структурированных данных.
- Комментарии только там, где логика неочевидна. Никаких заглушек `pass  # TODO` в сдаваемом коде — только рабочий код.
- Логирование через `utils/logger.py`, никаких `print()`.
- Ошибки: свои исключения в `core/errors.py`, наверх пробрасывается типизированное исключение, не голый `Exception`.
- Все внешние вызовы (сеть, аудио-устройства, WinAPI) обёрнуты в обработку ошибок с логом и понятным сообщением для пользователя.

## Конвенции данных
- Схема БД — миграции с версией в таблице `schema_version`. Не ломать существующие таблицы, только миграция вперёд.
- Формат экспорта команд — `.ayris` (JSON) с полем `schema_version`.
- Настройки: секции в `config.toml` соответствуют вкладкам настроек.

## Тема оформления
Тёмно-фиолетовая, футуристичная, минималистичная. Цветовые токены в одном месте (`resources/themes/`), никаких хардкодов цветов в виджетах. Оверлей: Topmost, не перехватывает фокус, per-monitor DPI aware.

## Правила работы в чате-задаче
1. Прочитай задачу целиком, затем нужные существующие файлы проекта — не переписывай то, что уже работает.
2. Меняй только файлы, перечисленные в задаче (плюс регистрация в реестре/индексе, если требуется).
3. Пиши рабочий код, а не каркас. Если что-то нельзя проверить без реального оборудования — скажи об этом прямо.
4. После кода: `ruff check`, `mypy src`, `pytest` (если тесты есть в объёме задачи). Оставляй проект в рабочем состоянии.
5. В конце отметь `[x]` для своей задачи в `AYRIS_ROADMAP.md` и одной строкой опиши, что появилось и какие интерфейсы теперь доступны следующим задачам.
6. Если задача упирается в непринятое решение — задай один вопрос, не изобретай архитектуру молча.

## Порядок выполнения
Идти по номерам. Зависимости указаны в каждом файле задачи и в `AYRIS_ROADMAP.md`. Этапы A–C — фундамент, без них остальное не поедет.
